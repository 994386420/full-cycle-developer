# 阶段 2：制定 Plan 与规范分发

1. 读取需求正文及涉及当前范围的全部附链，登记来源版本/章节和读取结论。来源不能读时保留 `pending`/`blocked`，不能编造内容。
2. 使用可用的设计连接器读取整页、状态、节点尺寸和资源。蓝湖优先使用设计 ID、不可变快照和局部检查工具；Figma 使用官方 MCP。设计白膜/空白不能作为依据。
3. 搜索现有组件、状态、Provider、模型、枚举、API 常量和调用方。把需求、设计与代码三方差异逐条写入 `tasks`。
4. 每条任务给出稳定 ID、来源的具体位置、类别、影响范围、需要遵守的规则和验收条件。UI 明确何时出现/隐藏，验收条件明确状态、数据、观察方式与预期值；不能只写“体验良好”。
5. 为六类覆盖写明涉及的任务 ID 或不适用原因。独立加入一条 `integration` 任务，验真实入口、数据、渲染与组合使用。
6. 规范分发：回读每条任务对应的项目规则，将具体章节填入 `rules`。顺序执行也要做此检查，不因没有子代理而省略。
7. 将来源冲突、缺失状态和需拍板的架构/接口/依赖列入 `decisions`。有现成授权的按授权执行；真正影响实现且无法推断的才向用户提问。

`decisions` 的阻塞项未解决不能过 Gate。解决项写清 `resolution` 与 `authority`（本轮用户决定、已确认接口契约等），不把模型自己的推测当作授权。

更新 `plan.json` 后运行 `render`、`gate --stage 2`。本阶段不修改业务代码。
