# 阶段 4：逐项实现、自验与返工

按任务依赖顺序实施。任务包包括 ID、需求出处、允许修改范围、规范、验收条件、场景位置和产物路径。会话已允许子代理时，可分发互不冲突的任务；同一共享文件的写入串行化。每个执行者先查已有探索事实，不在共享探索笔记里散播未经验证的“踩坑结论”。

实现一项就验一项。新测试仅用于有意义的行为边界和回归，不为可逆小改动堆同构测试。检查现有诊断基线，明确旧失败与本次新增问题。

验证循环：确认本地代码生效 → 断言实际状态 → 截图/运行验证 → 记录差异及根因 → 同轮集中修复 → 在相同条件下复验。截图分数与数值对账并行参考，不能为提分删除正确业务内容。

将实际日志或截图存入任务目录后登记：

```bash
python3 "$SKILL_DIR/scripts/workflow.py" record --root "$PROJECT_ROOT" --task-dir "$TASK_DIR" \
  --task T1 --criterion C1 --kind widget --file evidence/T1-widget.txt \
  --result pass --actual "目标断言通过；共 8 项测试通过" \
  --context "实际执行的命令、环境、样本与断言范围" \
  --watch lib/feature/page.dart --watch test/feature/page_test.dart
```

`record` 只登记执行者的真实观察，不会代替运行测试或判读截图。`--watch` 应覆盖该结论依赖的实现、测试、共享逻辑及配置；源码变化后 Gate 会拒绝过期证据。修复后重新生成证据再登记，不能仅重新计算指纹。

每个 UI 闭环包含原始截图、对比报告、数值对账、差异清单以及每条差异的处理和复验。子代理须先落盘再汇报；主执行者读取产物，不只信“已完成”消息。不将静默自动判为代理失联；工具缺失时直接顺序处理。

主执行者亲自复核整体形态和组合任务，尤其入口→接口/仓储→页面，以及刷新、重开、返回和持久化链路。初始化改动进行冷启动验证；临时假数据不能充当真实服务证据。

做不到的验证保留真实状态，在 `handoff` 按任务和条件登记负责人、原因和下一步。可以交付有明确待验项的代码，但结果只能是 `partial`。反复失败且无新证据时停止盲目重试，先补定位。

Gate：实现与每条验收条件都有结论；通过项有当前有效的证据，未通过项有交接。脚本通过后仍须审阅证据内容和与条件的对应关系。
